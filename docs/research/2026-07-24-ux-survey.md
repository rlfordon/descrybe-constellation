# UX survey — coordinated filtering, panes, reading view, graph legibility, chrome

**Date:** 2026-07-24. Research-only; no code changed by this pass. Answers the nine
questions in the UX/UI backlog item (`docs/backlog.md`, "UX/UI pass"). Method:
`WebSearch`/`WebFetch` against comparable graph-exploration tools, legal-research
UIs, and general UX-pattern literature. Every external claim is cited inline;
where I could not verify a product's UI firsthand (no working account / no
public screenshots), I say so rather than describe it from memory.

Baseline (current app, read before researching): three fixed-width panes
(`static/index.html`, `static/style.css` — `#pane-left`/`#pane-right` at
`width: 300px`, `#pane-center` flexible), Cytoscape.js graph with force/timeline
layouts (`static/app.js` `renderGraph`/`layoutTimeline`), a static legend
(`#legend` in `index.html`), an issue filter that lives entirely in the left
pane today (`#issue-filter` block, `renderIssueFilterCount` in `app.js`), a
right pane with Case/Leading tabs, and a 5-button header
(`#layout-toggle`, `#export-trail`, `#export-snapshot`, `#view-dossier`,
`#export-dossier`).

## 1. Coordinated filtering: keeping filter state visible and consistent

**Recommendation.** Give the issue filter one persistent, always-visible status
element — not a hidden panel — showing three things at once: the active filter
terms, a "N of M match" count, and a one-click clear action. Apply the *same*
visual treatment (today: 0.12-opacity dimming) to every coordinated view, not
just the graph: right now `renderGraph` dims non-matching nodes/edges
(`app.js` lines 172–177) but the Leading-cases table (`renderLeadingTab`) and
the case card have no equivalent treatment — a filtered-out case can still
appear ranked #1 in the Leading tab with no visual signal that it's dimmed on
the graph.

**Evidence.**
- The coordinated-multiple-views / brushing-and-linking literature is explicit
  that a selection or filter made in one view must be broadcast and rendered
  consistently in every linked view, not just applied silently to the
  underlying data — otherwise views drift out of sync with each other in the
  user's mental model. See the foundational surveys: [State of the Art:
  Coordinated & Multiple Views in Exploratory
  Visualization](https://www.cs.kent.ac.uk/pubs/2007/2559/content.pdf) and
  [Multiple and Coordinated Views in Information
  Visualization](https://www.mmi.ifi.lmu.de/lehre/ws0809/hs/docs/scherr.pdf).
- SAP Fiori's **Filter Feedback Bar** is a named, documented pattern for
  exactly this problem: a persistent bar, separate from the filter *controls*,
  that always shows the current filter's summary and result count —
  [SAP Fiori for Android: Filter Feedback
  Bar](https://experience.sap.com/fiori-design-android/filter-feedback-bar/).
- General filter-UX guidance converges on the same point: active filters
  should be visible as chips/a summary "at all times," with counts shown
  before commitment where possible — [Setproduct: Filter UI
  design](https://www.setproduct.com/blog/filter-ui-design), [Pencil & Paper:
  Filtering UX](https://www.pencilandpaper.io/articles/ux-pattern-analysis-enterprise-filtering),
  [UXPin: Filter UI and UX
  Design](https://www.uxpin.com/studio/blog/filter-ui-and-ux/).

**Change list for constellation.**
- Add a small always-visible filter-status element (terms + "N of M match" +
  Clear) that renders identically regardless of which right-pane tab is
  active — see §2 for placement.
- Extend `renderLeadingTab` to receive `issue_match` per row and render
  non-matching rows with the same dimmed treatment as the graph (e.g. a
  `.dim` row class at ~0.4 opacity — full 0.12 is likely too low for readable
  table text). Confirm the `/api/corpus` and `/api/expand` payloads already
  carry `issue_match` on `ranked_top`/`foundational` entries; if not, that's a
  small backend addition (same field the graph nodes already get).
- Add the same dim indicator to the case card when the currently-loaded case
  doesn't match the active filter, so a user who reached the card via search
  or a stale reference sees the same signal.

## 2. Filter placement: where on the "review" side

**Recommendation.** A **persistent bar pinned above the tab strip** in
`#pane-right` (above `.tabs`, so it's visible whether the Case or Leading tab
is active) — not inside the graph toolbar (the graph pane has no toolbar today,
just the legend overlay) and not duplicated per-tab. This reads as a
review/analysis control per the maintainer's decision, sits where both
coordinated views (graph + Leading table) can see its state, and avoids the
failure mode of a per-tab filter where switching tabs hides whether a filter
is active.

**Evidence.**
- Master-detail interfaces conventionally place list-scoped controls (search,
  filter, sort) at the top of the list/detail region, not inside the record
  editor or the builder screen that produced the list — general pattern
  description: [Windows Dev Blog: Master-Detail
  Pattern](https://blogs.windows.com/windowsdeveloper/2017/05/01/master-master-detail-pattern/),
  [Microsoft Learn: List/details
  pattern](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/list-details).
- Westlaw's own separation supports the same build/analyze split the
  maintainer already decided on: query construction happens on the search
  screen, but citing-reference filters (jurisdiction, date range, reported
  status) live in a **Filters** panel attached to the results view itself —
  [Stanford Law Library: Citing References /
  Citing Decisions](https://guides.law.stanford.edu/cases/citingreferences).
- The SAP Filter Feedback Bar (§1) is explicitly a bar above the filtered
  list, reinforcing "top of the results region" as the placement convention
  rather than embedding filter controls in the data-producing screen.

**Change list for constellation.**
- Move the `#issue-filter` block (`index.html` lines 62–70) out of
  `#pane-left` and into a new element inside `#pane-right`, rendered before
  `.tabs`. Keep the input + Filter/Clear buttons there; add the status element
  from §1 next to them, not below in a separate `.hint` div that's easy to
  miss (current `#issue-filter-status` styling is a barely-visible 0.75rem
  gray line — bump contrast/weight given its new job as the primary "you are
  looking at a filtered view" signal).
- No backend change needed — this is a DOM relocation plus CSS.

## 3. Resizable panes: implementation conventions

**Recommendation.** Standard three-region drag-handle pattern: a ~6–8px
`.resize-handle` element between `#pane-left`/`#pane-center` and
`#pane-center`/`#pane-right`, pointer-events (`pointerdown`/`pointermove`/
`pointerup`) updating each side pane's width in pixels (not `%`, so the center
pane keeps `flex: 1` and absorbs remaining space), clamped to a min-width
(≈220px for the side panes; the center pane's Cytoscape container needs a
floor too, ≈360px, or the graph becomes unusable), and the resulting widths
persisted to `localStorage` and reapplied on load before Cytoscape
initializes.

**Evidence.**
- Vanilla-JS build-from-scratch walkthroughs, matching this app's "no
  framework" constraint: [OpenReplay: Creating Resizable Split Panes from
  Scratch](https://blog.openreplay.com/resizable-split-panes-from-scratch/),
  [Madras Academy: Building a Resizable Split Screen
  Layout](https://www.madrasacademy.com/building-a-resizable-split-screen-layout-with-html-css-and-javascript/),
  [ExeIdeas: Resizable Split DIVs Using Pure
  JavaScript](https://www.exeideas.com/2022/10/create-resizable-split-divsusing-javascript.html).
- Reference for constraints and persistence conventions (min-size flex ratios,
  `onResize` callback saving to `localStorage`):
  [ResizerTwo.js](https://www.cssscript.com/split-view-resizertwo/).
- The flexbox gotcha that will bite here: flex children don't shrink below
  their content's intrinsic size unless `min-width: 0` is set on both the
  container and the resizing children — documented in the OpenReplay
  walkthrough above; `#pane-left`/`#pane-right` currently have no such rule
  (`style.css` lines 48–57), so this must be added alongside the resize
  handles or dragging narrow will fight the browser's default flex-basis
  behavior.

**Change list for constellation.**
- Two `.resize-handle` divs in `index.html` between the three `<section>`
  panes.
- CSS: `min-width: 0` on `#pane-left`, `#pane-right`, and `#pane-center`;
  handle styling (`cursor: col-resize`, hover highlight).
- JS: drag logic + `localStorage` keys (e.g. `constellation.paneLeftWidth`,
  `constellation.paneRightWidth`), applied on page load.
- **Cytoscape-specific note** (not from a citation — a known library
  requirement): Cytoscape.js sizes its canvas from the container's dimensions
  at init/layout time and does not auto-detect a parent flex-resize. Call
  `cy.resize()` (and re-run the active layout, or at least `cy.fit()`) on
  `pointerup` after a drag that touches `#pane-center`'s width, or the graph
  canvas will be visually stale/clipped until the next full re-render.
  Pure JS, no backend.

## 4. Hideable/collapsible panes: should we?

**Recommendation.** Qualified, narrow yes: collapse-to-icon-rail is reasonable
for **`#pane-left` only**, and only as a lower-priority follow-on to resizing
(§3) rather than a requirement — a user can already shrink the left pane once
resizing ships, which covers most of the motivating case. Do **not** collapse
`#pane-right`: it's the primary always-consulted analysis surface (case card +
Leading table + the new filter bar from §2), and coordinated-views practice
depends on linked views staying visible so filter/selection state stays
legible (§1). Collapsing it contradicts that.

This recommendation carries a caveat the maintainer should weigh: I could not
find precedent for collapsing a panel that is itself full of *live, editable
model state* (search terms, variant list, threshold, cluster chips) — the
icon-rail pattern's precedent base is almost entirely **navigation** sidebars
(menu items, not form controls). Collapsing a nav rail loses nothing but a
menu the user can reopen; collapsing this left pane hides in-progress
corpus-building state the user may need to revisit (add a variant, nudge the
threshold, re-run search). That's a materially different risk profile than
the precedent supports, and it echoes the exact failure mode Nielsen Norman
Group warns about for progressive disclosure generally (§5): splitting
interdependent controls across a visibility boundary causes errors when users
need to move between them. Treat this as "adopt experimentally, watch for
users who forget corpus-building state exists," not "adopt with confidence."

**Evidence.**
- Icon-rail collapse as the standard SaaS/admin sidebar pattern, with
  collapsed state in `localStorage`: [DEV: Building a Collapsible Admin
  Sidebar](https://dev.to/cristiansifuentes/building-a-collapsible-admin-sidebar-with-react-router-uselocation-pro-patterns-7im),
  general sidebar-navigation pattern writeups: [UI Potion: Sidebar
  Navigation](https://uipotion.com/potions/components/sidebar-navigation).
  Note these are consistently framed around *navigation* items, not editable
  form state — this is the gap flagged above.
- The countervailing argument (keep it visible) comes from the same
  progressive-disclosure caution cited in §5: NN/g's hotel-booking example
  shows that separating interdependent controls (payment vs. room selection)
  across screens increased errors — [NN/G: Progressive
  Disclosure](https://www.nngroup.com/articles/progressive-disclosure/).

**Change list for constellation.** Defer. If pursued: collapse `#pane-left` to
a narrow icon rail (single icon, e.g. a magnifying glass) below some width
threshold or via an explicit toggle button in the header; persist
collapsed/expanded to `localStorage`; do not collapse `#pane-right`. Pure
CSS/JS, no backend.

## 5. Build-flow progressive disclosure (left pane)

**Recommendation.** Section the left pane into visually distinct, **always
reachable** stages — seed/jurisdiction/search always visible; variants +
cluster chips + threshold revealed (expanded by default, collapsible after
first use) once a search has run; hop controls enabled-but-visible once a
corpus is built — using accordion/`<details>`-style disclosure, not a
hide-until-later or wizard/step pattern. The distinction matters: NN/g
explicitly contrasts progressive disclosure (defer *secondary* features) with
staged/wizard disclosure (step through a *linear* sequence), and warns staged
disclosure breaks down "when steps are interdependent and users must
alternate between them" — which is exactly this workflow's shape: a user
adjusts the threshold, re-reads clusters, adds a variant, searches again,
*then* builds a corpus, and later still may want to run another hop and
recheck the original variants. Nothing here should become unreachable once
"used."

**Evidence.**
- [NN/G: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/) —
  core guidance on splitting initial vs. secondary options by frequency of
  use, and the staged-vs-progressive distinction with the hotel-booking
  counterexample (interdependent steps → errors when forced linear).
- General progressive-disclosure summaries reinforce accordions/expandable
  sections as the standard implementation for "defer but keep reachable" (vs.
  modals/wizards for strictly linear tasks): [UXPin: What Is Progressive
  Disclosure](https://www.uxpin.com/studio/blog/what-is-progressive-disclosure/).

**Change list for constellation.**
- Wrap the `#variants` block and the threshold slider in a `<details>` (or
  equivalent JS-toggled section) that starts open, with a persistent one-line
  summary when collapsed (e.g. "3 variants, threshold 0.5") so state is
  legible even collapsed.
- Add lightweight stage labels ("1. Search", "2. Refine clusters", "3. Build
  corpus", "4. Expand") as section headers rather than hiding earlier stages —
  scaffolding, not gating.
- Keep `#hop-controls` visible-but-disabled pre-corpus (current behavior via
  the `disabled` attribute is already correct here — don't hide it).
  Pure CSS/JS, no backend.

## 6. Long-document reading pane (case-reader feature)

**Recommendation.** Reading view **replaces the Case tab's content in
`#pane-right`** (not a new column, not a full-page overlay) — reached via a
"Read full opinion" action on the case card, with a sticky "← Back to case
card" affordance at the top so the card is never more than one click away.
Layout inside that space:
- A thin **passage-nav strip** pinned at the top: "N of M issue passages",
  prev/next arrows.
- The opinion text below, scrollable, with issue-matched passages highlighted
  in a single warm highlight color (amber/yellow, low-opacity background) —
  one color is enough for this app's single "issue focus," unlike Westlaw's
  multi-color Select Highlighting, which exists because Westlaw lets users
  track *several* distinct term sets at once.
- A **scrollbar-gutter overlay** with tick marks at each passage's vertical
  position in the document, click-to-jump — the browser find-in-page pattern,
  reused.

The open feasibility question flagged in `backlog.md` ("passage→opinion-text
anchoring... under measurement") is real and matters more than the layout
choice: Descrybe's `get_case_passages` returns prose snippets, not character
offsets into a specific opinion-text rendering (`docs/spike-findings.md` F3),
and the full opinion text isn't fetched anywhere in the app today
(`docs/design.md` line 39: "full opinions are never fetched for browsing").
So this is two problems, not one: (a) a new backend call to fetch full opinion
text (CourtListener `opinions` endpoint) plus caching, and (b) matching each
passage string into that text despite likely whitespace/formatting drift
between Descrybe's extraction and CourtListener's stored text.

For (b), the applicable precedent is Hypothes.is's **anchoring** approach:
rather than requiring exact offsets, it matches an annotation's quoted text
(plus optional surrounding context) fuzzily against the live document, so
annotations survive re-renders and minor text differences — this is the same
shape of problem (matching remembered text against a possibly-different
rendering of "the same" document). Recommend implementing an equivalent
fuzzy-text-quote match (normalize whitespace, then approximate substring
search) per passage, and gracefully labeling any passage that can't be
located (using the app's existing `[Needs verification]` source-label
convention from `docs/design.md` §7) rather than silently dropping it.

**Evidence.**
- Westlaw Select Highlighting + term-navigation arrows + heat map: highlighted
  terms are navigable via arrows and a TOC-panel term list, plus a heat map
  showing where highlighted terms concentrate section-by-section —
  [Thomson Reuters: Find Westlaw Results Faster with Highlighting and Heat
  Mapping](https://legal.thomsonreuters.com/en/insights/articles/find-westlaw-results-faster-with-highlighting-and-heat-mapping).
- Browser find-in-page scrollbar tick marks, directly transferable to a
  passage-locations overlay: Chrome's "At-a-Glance Tick Bar" and Firefox 87's
  scrollbar match highlights — [ghacks: Firefox 87 find-on-page highlights
  matches in
  scrollbar](https://www.ghacks.net/2021/02/14/firefox-87-find-on-page-highlights-matches-in-scrollbar/).
- VS Code's find widget: Enter/Shift+Enter steps between matches, matches also
  render in the minimap, with an explicit cap (>1000 matches → reduced
  decoration) worth mirroring if a passage list gets long —
  [VS Code Basic Editing docs](https://code.visualstudio.com/docs/editing/codebasics),
  [VS Code minimap search issue
  #76030](https://github.com/microsoft/vscode/issues/76030) (documents the
  1000-match cap behavior).
- Hypothes.is anchoring: matches quoted text (and surrounding context)
  against the live document rather than relying on stored offsets, which is
  what makes annotations resilient to re-rendering — [Hypothesis: What's the
  difference between an annotation and a
  highlight?](https://web.hypothes.is/help/whats-the-difference-between-an-annotation-and-a-highlight/),
  [hypothesis/anchoring-test-tools
  (GitHub)](https://github.com/hypothesis/anchoring-test-tools). I could not
  find public documentation of Hypothesis's exact fuzzy-matching algorithm
  (only that TextQuoteSelector/TextPositionSelector selectors exist and that
  anchoring test fixtures are maintained separately) — treat "use fuzzy
  text-quote matching" as the transferable *idea*, not a specific algorithm to
  copy.
- Genius.com's highlight system is a **weaker** precedent than it first
  appears: its highlights are computed from start/end indices into Genius's
  own canonically-stored lyrics text, which Genius fully controls — it isn't
  solving the cross-source matching problem this app has (Descrybe passage
  text vs. CourtListener opinion text, two different vendors). Noting this so
  it isn't over-cited as support.

**Change list for constellation.**
- Backend (**new scope**): fetch full opinion plain text from CourtListener
  (opinion endpoint), cache alongside existing per-case cache entries.
- Backend/logic: fuzzy passage-to-text matching function; returns match
  ranges or a "not locatable" flag per passage.
- Frontend: reading view replacing `#tab-case` content, back breadcrumb,
  highlight spans, prev/next nav bound to match ranges, scrollbar-tick overlay
  (same "recompute positions on resize/scroll" discipline the timeline-axis
  fix in §7 needs — don't repeat the static-overlay bug).
- Given the explicitly flagged feasibility uncertainty, recommend a short
  spike measuring fuzzy-match hit rate across a sample of cases *before*
  committing to the full reading-view build — if match rate is low, the
  highlight feature degrades to "full text, no highlights," which is a much
  smaller and still-useful fallback.

## 7. Graph legibility: legend, label density, axis-under-zoom, semantic zoom

**Legend.** Keep the legend always visible (current behavior is fine) and make
the **court-level color swatches** click-to-toggle (dim/hide that court level
across the graph), leaving origin shapes and the foundational ring
non-interactive — they're rarely something a user wants to suppress, and
adding interactivity to every legend row adds noise for little payoff.
Interactive-legend-as-filter is a well-established, low-risk pattern:
[Flourish: transforming charts with
filters](https://flourish.studio/blog/chart-filters/), [Vega: Interactive
Legend Example](https://vega.github.io/vega/examples/interactive-legend/),
[Esri: Create simple filter apps with Interactive
Legend](https://www.esri.com/arcgis-blog/products/instant-apps/mapping/interactive-legend).
This is a second, orthogonal filter axis from the issue filter (§1/§2) —
encoding-level vs. content-level — and should be visually distinct from it so
the two aren't confused.

**Label density.** Implement zoom-tiered label visibility: hide node labels
below some zoom threshold, reveal them progressively (highest-`citation_count`
nodes first) as the user zooms in, matching the general "rank until a
density/occlusion threshold is crossed" strategy used in large-network
tooling — [Cambridge Intelligence: Graph visualization at
scale](https://cambridge-intelligence.com/visualize-large-networks/) (general
adaptive-styling-by-zoom-level framing; the article does not give a specific
algorithm, so treat this as directional, not a recipe). Concretely: a
Cytoscape style function keyed on `cy.zoom()`, similar in shape to the
constant-size fix below.

**Timeline axis under pan/zoom (bug #1 in backlog.md).** Confirmed correct
approach: recompute the overlay on `cy` `pan`/`zoom` events, as the fix sketch
already proposes. The general technique — re-derive the axis scale from the
current zoom transform and redraw ticks on every pan/zoom event — is exactly
what D3's canonical pattern does via `transform.rescaleX()`/`rescaleY()`:
[Observable: Pan & Zoom Axes](https://observablehq.com/@d3/pan-zoom-axes),
[d3-zoom docs](https://d3js.org/d3-zoom). Recommend going further than the
backlog's hand-rolled sketch: pull in `d3-scale` + `d3-axis` (small,
independent modules, no need for the rest of D3) for the timeline-axis layer
specifically, rather than hand-computing tick positions and labels in
`renderTimelineAxis`. The hand-rolled version will eventually need to
reimplement things d3-axis already does for free — "nice" round-number tick
selection, collision-avoidance between adjacent labels, consistent tick
formatting — and an older hand-rolled example of exactly this pan/zoom/axis
problem documents a known bug from taking the manual-recompute path (double
rescale + pan interaction reintroduces stale state):
[gist: D3 zoom, pan, and axis rescale](https://gist.github.com/1182434/be4191366e746420ac3d658f7ec6e41c9135abb9).
This is additive, doesn't require migrating the rest of the graph rendering
off Cytoscape.

**Semantic zoom (bug #2 in backlog.md).** The underlying technique — divide
node width/height and font size by `cy.zoom()` so glyphs hold constant screen
size while positions spread apart on zoom-in — is sound and should be
implemented; it's a specifically, repeatedly requested feature in comparable
force/network libraries for exactly this overlap-resolution reason (e.g. three
separate vis.js/vis-network GitHub issues asking for constant node/font size
under zoom: [#3462](https://github.com/almende/vis/issues/3462),
[#1838](https://github.com/visjs/vis/issues/1838),
[#1681](https://github.com/visjs/vis/issues/1681)).

Worth flagging a terminology nuance, not a substantive objection: sources
disagree on whether "constant size, growing separation" *is* semantic zoom or
a different, narrower technique. The narrowest definition I found (InfoVis
Wiki) matches the backlog's plan directly — objects "stay the same size but
are just further apart when you zoom in" is offered there as one description
of semantic zoom, in contrast to geometric zoom where objects simply get
bigger: [InfoVis Wiki: Semantic
Zoom](https://infovis-wiki.net/wiki/Semantic_Zoom). But most other treatments
define semantic zoom by a *qualitative* change in the information shown at
different scales — more detail, different representations, not merely more
spacing — [Fraunhofer: Semantic Zooming for Ontology Graph
Visualizations](https://publica.fraunhofer.de/bitstreams/db3899b7-9ee3-4f2e-8a32-e1b034242f18/download),
[emergentmind: Semantic Zoom topic
summary](https://www.emergentmind.com/topics/semantic-zoom). Practical
takeaway: build the constant-size fix (it's correct and well-precedented
regardless of what it's called), and treat the **label-density** tiering above
as the actual semantic-zoom layer on top of it — that's where genuinely
different information gets shown at different scales (which labels are
visible, how much metadata is shown), and the current plan doesn't yet include
it.

**Change list for constellation.**
- Legend: click handler on court-level swatches → toggle a `.hidden-court`
  class / Cytoscape selector-based hide on matching nodes. CSS/JS only.
- Label density: Cytoscape style function bound to a `zoom` event listener,
  toggling label opacity/display by rank. CSS/JS only.
- Timeline axis: add `pan`/`zoom` listeners calling
  `renderTimelineAxis` with recomputed gutter/plotW/laneH from current
  `cy.zoom()`/`cy.pan()`; consider swapping in `d3-scale`+`d3-axis` for tick
  generation (new, small dependency — first non-Cytoscape JS dependency in the
  project, worth a deliberate call given the "no framework, no build step"
  convention in `app.js`'s header comment; d3-scale/d3-axis are usable via a
  plain `<script>` UMD build with no bundler, so this doesn't violate that
  constraint, but it's a new vendor file to add under `static/vendor/`
  alongside `cytoscape.min.js`).
- Constant-size zoom: `zoom` event handler dividing node width/height/font-size
  by `cy.zoom()`; apply to both force and timeline layouts as the backlog
  entry suggests. CSS/JS only.

## 8. Header/toolbar consolidation

**Recommendation.** Collapse the four export/view buttons into three visible
controls: **[Force/Timeline toggle] [View Dossier] [Export ▾]**, where Export
opens a small dropdown with "Export dossier," "Export trail," "Export
snapshot." Keep "View Dossier" separate from the Export menu — it's a *view*
action (opens `/dossier` in a new tab), semantically different from the three
*download* actions, and collapsing it into "Export" would bury a
frequently-used action behind a click for no grouping benefit.

This isn't yet at the scale where a command palette (Cmd+K) helps — that
pattern is recommended once an app has "10+ navigable pages or actions"
([uxpatterns.dev: Command Palette
Pattern](https://uxpatterns.dev/patterns/advanced/command-palette)); this app
has 5 header actions today, and consolidating to 3 removes the near-term
pressure. Revisit if per-node context actions or additional export formats
push the action count up substantially.

**Evidence.**
- PatternFly's overflow-menu guidance: avoid more than 3 fully-displayed
  toolbar actions, move less-primary actions into an overflow/menu control,
  position it consistently (right side) —
  [PatternFly: Overflow Menu design
  guidelines](https://www.patternfly.org/components/overflow-menu/design-guidelines/).
- Carbon Design System documents an explicit **export pattern** — grouping
  multiple export formats/targets under one export control rather than one
  button per format. (I could only retrieve a partial/truncated fetch of
  [Carbon's export pattern
  page](https://carbondesignsystem.com/community/patterns/export-pattern/);
  treat the "group multiple export types under one menu" claim as
  directionally supported by that page's title/URL and by the general
  overflow-menu literature above, not as a verified quote from Carbon's full
  guidance — I was not able to confirm the specifics firsthand.)
- General toolbar-overflow guidance converges on "expose 2–4 most-common
  actions, move the rest to an overflow control," e.g. shadcn's
  [Overflow Menu](https://www.shadcn.io/examples/button-group-overflow-menu)
  and [Contextual
  Toolbar](https://www.shadcn.io/patterns/button-group-patterns-2) pattern
  writeups.

**Change list for constellation.** Replace the three `export-*` buttons in
`index.html`'s `.header-actions` with a single "Export ▾" button that opens a
small absolutely-positioned menu (reuse the `.chip`/dropdown styling already
established elsewhere in `style.css`, or a native `<details>`/`<summary>` for

## 9. Empty states and first-run

**Recommendation.** Apply NN/g's three-part framework — communicate system
status, offer a learning cue, provide a direct pathway to the next action —
to every pane's pre-data state, not just the one that already has it
(`#case-empty`).

| Location | Current state | Recommended empty state |
|---|---|---|
| `#pane-left`, pre-search | Empty textarea + placeholder | Fine as-is; optionally add one line under the Search button: "Search returns case clusters you can prune before building a corpus." (learning cue) |
| `#pane-center` (`#cy`), pre-corpus | Blank canvas, no message | Add an overlay message: "No corpus yet — search and build a corpus on the left to see the citation graph." (status + pathway) |
| `#tab-case`, pre-selection, no corpus | `#case-empty`: "Click a node in the graph to view a case." | Split into two states: pre-corpus ("Build a corpus, then click a node to view a case") vs. post-corpus/pre-selection (current text is fine here) — the current single message is misleading before any corpus exists, since there's nothing to click yet. |
| `#tab-leading` | No empty state; renders an empty table/list silently | Add: "Leading and foundational cases will appear here once you build a corpus." |
| Filter status (§1/§2) | No message when unfiltered | Add a neutral state: "No filter applied — showing full corpus," so silence isn't mistaken for a bug. |

**Evidence.** [NN/G: Designing Empty States in Complex
Applications](https://www.nngroup.com/articles/empty-state-interface-design/) —
the three guidelines (system status, learning cues, direct pathways), and the
article's own generalization that this applies whether the cause is
onboarding, an unconfigured feature, or a filter/search returning nothing.

**Change list for constellation.** All copy + small conditional-render logic
in `app.js` (toggle overlay/message elements based on `corpusBuilt` and
current filter state, already tracked in existing variables). No backend
changes.
